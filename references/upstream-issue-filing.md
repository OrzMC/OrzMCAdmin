# 把问题整理成上游 issue（OrzMC 系）

用户验证软件偏好「不改上游代码、只把问题整理成文档交上游」，所以遇到插件自身缺陷（不是自己配置错）时，交付物是一份可提交的 issue，不是本地 patch。

## 1. 仓库与工具面

- 插件/程序源码：`OrzMC/OrzMCPlugin`（父仓 `OrzMC/OrzMC` 只放 submodule 指针）。
- **issue 开在 `OrzMC/OrzMCPlugin`**，不是父仓。开之前 `gh issue list --repo OrzMC/OrzMCPlugin --state open --json number,title,labels` 查重（列表里会混着 `automation`/`quality-trend` 这类机器维护的看板 issue，别误当同类问题）。
- 正文写长文时用文件传，别塞命令行：`gh issue create --repo … --title … --body-file <path>`（body 里有反引号/换行/表格时 `--body` 必翻车）。
- **提交后回读验证**（外部写入必须读回）：`gh issue view <n> --repo … --json number,title,state,url,body --jq '{number,state,url,body_len:(.body|length)}'` —— 确认 state=OPEN、body 长度正常（长度骤小=截断）。
- 别在 issue 里贴 token/密钥/连接串；日志摘录先把凭据打码成 `[REDACTED]`。

## 2. 正文骨架（按这个顺序写，上游一眼能复现）

1. **现象**：日志原文摘录（带时间戳/线程名）+ 一张统计表（次数/频率/持续时间），把「偶发」变成可量化事实。
2. **环境**：核心版本、插件版本（从 Jar 文件名不可靠，看启动日志的 `Enabling <插件> v…`）、JDK、关键配置项（如 `backend: builtin`、哪些平台 enabled）。
3. **已排除**：逐条列你排除掉的可能性 + 证据（网络实测延迟/成功率、同类组件日志计数对比、空服对照）。这一节决定 issue 质量——没有它，上游第一句就会问「是不是你网络问题」。
4. **推测原因**：指出判活/阈值/时序层面的机制错位（例如「静默检测把有无应用层消息当断线，而空闲期只有 ws ping/pong」），明确说是推测。
5. **影响**：分条写对业务的实际后果（消息丢失窗口、通道长期不可用、日志噪声淹没真告警、频繁鉴权可能被限流）。
6. **期望**：给 2–3 个可选的正确行为（修判活依据 / 阈值可配置 / 至少降日志级别），别只写「希望修复」。
7. **复现方式**：最短的稳定复现（「空服挂 10–30 分钟看日志是否出现 X」优于一长串前置条件）。
8. **顺带发现**：顺手看到但不同源的问题单独一节，标明「同源误报/过期配置」——用户重视这类附带信息，但混进主问题会让上游难定位。

## 3. 判定「这是上游问题还是我的配置问题」

先自我排除三条，任一条成立就别开 issue（开本地工单/改配置）：

- 出网/DNS/代理：在**服务运行的那个环境里**（常常是 WSL 或容器内，不是宿主 Git-Bash）实测目标域名 3 次，看延迟与成功率；
- 配置项：确认 `backend`/开关/白名单确实指向被测路径（例如 `backend: builtin` 时，经过 easybot 的日志就与该问题无关）；
- 历史对照：翻 `logs/*.log.gz` 抓告警计数，区分「本次新出现」还是「长期存在但无人看」，并写进 issue（例如「最近 40 次会话仅 2 次出现该告警，均在长时空闲会话」极能帮上游定位）。

> 统计历史归档时 `zcat` 在 Git-Bash 下不一定有，统一走 `wsl.exe -d Ubuntu -e sh -c 'zcat … | grep -c …'` 并 `| tr -d '\0'`。
